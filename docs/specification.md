# Claude-Code-Sitzungsverwaltung – Spezifikation

Dieses Dokument beschreibt ein selbst gehostetes Web-Frontend, mit dem Claude-Code-Sitzungen auf dem Heimserver verwaltet werden. Es dient als Arbeitsgrundlage für eine Implementierungs-Session.

## Ziel und Motivation

Auf dem Server liegen inzwischen viele Repositories. Die bisherigen Wege (Devbox-VM per RDP im Browser, CloudCLI, T3 Code) sind umständlich, vor allem beim Umgang mit Git-Worktrees. Außerdem fehlt die Möglichkeit, mehrere Repositories in derselben Konversation zu bearbeiten. Das neue Frontend soll Sitzungen, Repositories und deren Arbeitskopien an einer Stelle bündeln.

**Grundprinzip volle Rechte:** Das Frontend ist keine Sandbox, sondern ein Web-Frontend für Claude Code auf der Maschine, auf der es läuft (der Devbox des Besitzers). Eine Sitzung kann alles, was eine Claude-Code-Sitzung kann, die der Nutzer auf dieser Maschine im Terminal oder in der GUI startet: dasselbe `~/.claude` (Login, Skills, Plugins, MCP-Server, Memory, CLAUDE.md, Einstellungen), dieselben Git- und GitHub-Zugangsdaten (`gh`-Login, SSH-Schlüssel), `sudo`, Geräte, Docker, das ganze Dateisystem. Was das Frontend dazugibt, bleibt: Sitzungsverwaltung, Multi-Repo-Sitzungen mit eigenen Klonen pro Sitzung (Isolation paralleler Sitzungen voneinander), PR-Automatik, Benachrichtigungen und PWA, Vorschauen, die mobile Oberfläche.

**Grundprinzip Multi-Repo:** Eine Sitzung arbeitet von Anfang an mit beliebig vielen Repositories gleichzeitig. Datenmodell, Verwaltung der Sitzungsklone, Diff-Ansicht, Dev-Server-Vorschau, GitHub-Referenzen, PR-Automatik und Aufräumen sind deshalb immer pro Sitzung mit mehreren Repos ausgelegt, nie mit der Annahme „eine Sitzung = ein Repo“. Eine Sitzung kann damit auch mehrere PRs haben, einen pro geändertem Repository.

## Kernfunktionen

1. **Repository-Übersicht:** Der GitHub-Account ist angebunden. Beim Start einer Sitzung lassen sich alle Repositories auswählen, auf die der Account Zugriff hat, auch aus Organisationen. Ein gewähltes Repo wird beim ersten Mal als lokaler Spiegel ins Volume geklont, danach nur noch aktualisiert; jede Sitzung bekommt daraus einen eigenen Klon. Lokal vorhandene Repos werden mit Branch, Sitzungsklonen und Sitzungen angezeigt.
2. **Neue Sitzung starten:** Auswahl eines Haupt-Repositories plus optional weiterer Repositories. Für jedes gewählte Repository wird automatisch ein eigener Sitzungsklon mit neuem Branch angelegt.
3. **Neues Projekt ohne Repo:** Eine Sitzung kann auch in einem neuen, leeren lokalen Projekt gestartet werden, ganz ohne bestehendes GitHub-Repo. Das Projekt ist ein Repository ohne Remote (lokaler Spiegel mit `git init`); weitere Sitzungen arbeiten darauf wie auf jedem Repository in eigenen Klonen. Sitzungen ganz ohne Repository bekommen ein eigenes leeres Scratch-Verzeichnis. Bei Bedarf legt das Frontend über die GitHub App ein neues Repository im Account oder in einer Organisation an und verknüpft es als Remote.
4. **Multi-Repo-Sitzungen:** Das Haupt-Repository ist das Arbeitsverzeichnis, die weiteren Repositories werden als zusätzliche Verzeichnisse freigegeben. Auch einer laufenden Sitzung lässt sich ein weiteres Repository hinzufügen, damit Claude in derselben Konversation weiterarbeitet: in den Sitzungsdetails mit denselben Auswahlmöglichkeiten wie beim Start (registriertes Repository, GitHub, URL, lokales Projekt, Basis-Branch) oder durch Claude selbst über das Tool `add_repository`, das wie jedes Tool je nach Berechtigungsmodus nachfragt (die Freigabe zeigt Repository, Herkunft, Basis-Branch und Claudes Begründung). Das hinzugefügte Repository bekommt einen eigenen Klon auf dem Sitzungs-Branch, sein Setup-Skript läuft, und es verhält sich danach wie die übrigen (Diff, Push, PR, `@`/`#`, Aufräumen). Der laufende Claude-Code-Prozess übernimmt das Verzeichnis ohne Neustart, auch mitten im Turn. Scheitert der Klon oder das Setup-Skript, bleibt die Sitzung nutzbar; das Repository lässt sich erneut versuchen, trotzdem verwenden (nach fehlgeschlagenem Setup) oder wieder entfernen. Ein Repository aus einer laufenden Sitzung zu entfernen, ist nicht vorgesehen.
5. **Chat-Ansicht:** Live-Streaming der Antworten, Tool-Aufrufe und Dateiänderungen, jede Änderung direkt als Diff im Verlauf. Dazu eine Diff-Ansicht der gesamten Sitzung gegenüber dem Basis-Branch (ab der Merge-Basis wie bei einem Pull Request, sodass hereingemergte Änderungen des Basis-Branches nicht als Änderungen der Sitzung erscheinen), pro Repository und Datei, wahlweise nebeneinander oder untereinander; Eingabe neuer Nachrichten; Abbrechen einer laufenden Antwort.
   - **Umsetzung (entschieden):** Tool-Aufrufe sind unauffällige Zeilen ohne Rahmen, damit Claudes Text und die eigenen Nachrichten hervorstehen. Ab zwei aufeinanderfolgenden Aufrufen zwischen zwei Texten von Claude (samt Aufrufen und Text von Subagenten) zeigt der Verlauf eine einzige eingeklappte Zeile: Anzahl der Aufrufe, die verwendeten Tools bzw. der gerade laufende oder auf Freigabe wartende Aufruf, und wie viele fehlschlugen oder abgelehnt wurden. Aufgeklappt stehen die einzelnen Aufrufe mit ihren Freigabe-Zeilen darin; Diffs, gezeigte Dateien, Vorschauen und Pläne bleiben unter der Gruppe sichtbar.
6. **Sitzungen fortsetzen:** Liste aller Sitzungen mit Status (läuft, wartet, beendet). Beendete Sitzungen lassen sich über ihre Sitzungs-ID wieder aufnehmen.
   - **Umsetzung (entschieden):** „Wartet“ wird unterschieden: „Needs you“ (Freigabe, Rückfrage, Plan, fehlgeschlagenes Setup), „Ready“ (der Turn ist fertig, Claude wartet auf die nächste Nachricht) und „Background“ bzw. „2 background tasks“ (der Turn ist fertig, aber von Claude gestartete Hintergrund-Tasks wie Subagents, Hintergrundbefehle, Monitore oder Workflows laufen noch; Claude macht von selbst weiter, wenn sie sich melden). „Background“ erscheint wie „läuft“ (Farbe, Gruppe und Filter „Running“), zählt nicht als wartend auf den Nutzer, und eine Nachricht kann trotzdem gesendet werden. Einen Turn, den Claude Code danach von selbst beginnt, zeigt die App als „läuft“. Solange Hintergrund-Tasks laufen, wird der Prozess nicht wegen Leerlauf beendet. Wie Claudes eigene Angabe gilt auch „Background“ aus laufenden Tasks höchstens 30 Minuten nach dem Turn; danach ist die Sitzung „Ready“ (meldet „fertig“, Autofix darf laufen), auch wenn ein Task wie ein Dev-Server weiterläuft.
   - **Umsetzung (entschieden):** Claude kann den Wartezustand selbst angeben, mit dem Tool `set_waiting_state` (ohne Rückfrage): `user` (du bist dran, auch wenn z. B. ein Dev-Server im Hintergrund läuft) oder `work` mit kurzem Grund (z. B. „CI von PR #12“, ein Wakeup, ein Monitor), den die Oberfläche statt „Background“ als Status zeigt. Die Angabe ergänzt die automatische Erkennung und hat Vorrang; sie gilt bis zum nächsten Turn (nicht nach Stop, einem Fehler oder wenn eine wartende Nachricht direkt folgt), `work` höchstens 30 Minuten nach dem Turn, danach gilt die Sitzung ohne laufende Tasks als „Ready“ und meldet „fertig“. Ohne Angabe entscheiden die laufenden Hintergrund-Tasks. Während `work` gilt, wird der Prozess nicht wegen Leerlauf beendet.
   - **Umsetzung (entschieden, 2026-11-20):** Wartet die Sitzung auf die CI eines ihrer offenen PRs, erkennt die App das selbst und zeigt „Background“ mit „CI of #12“ statt „Ready“, auch wenn Claude `user` angegeben hat (Claude wartet dann nicht selbst, die App bringt das Ergebnis): für jeden offenen PR der Sitzung, mit oder ohne Autofix, solange Checks des Head-Commits laufen (höchstens 60 Minuten nach dem ersten Lesen) und bis zu einer Minute nach einem Push auf seinen Branch (gleich nach Claudes `git push`, bevor GitHub den neuen Head-Commit meldet) bzw. einem neuen Head-Commit, bis GitHub seine Checks listet (ein Repository ohne CI zeigt das also eine Minute nach jedem Push). Mit Autofix wartet die Sitzung nach den Checks weiter, bis die PR-Automatisierung sie angesehen hat (höchstens 2 Minuten), damit ein Autofix-Lauf oder die Bereit-Meldung ohne „Ready“ dazwischen folgt. „Fertig“ wird erst danach gemeldet, und nur einmal pro Turn: Beginnt das Warten ohne Turn (jemand anderes pusht auf den PR, Checks werden nach einem Neustart erneut gelesen), meldet sein Ende nichts. Wie bei `work` darf Autofix währenddessen laufen; der Prozess darf wegen Leerlauf beendet werden. Die Checks solcher Sitzungen werden wie die angesehener Sitzungen alle 30 Sekunden gelesen.
   - **Umsetzung (entschieden, 2026-11-20):** Hervorgehoben wird, wo Claude ohne den Nutzer nicht weitermacht: „Needs you“ (amber, Punkt mit Hof) und „Ready“ (Primärfarbe, Punkt mit Hof) als farbige Tags, „Failed“ rot. Sitzungen, die von selbst weitermachen („Running“, „Preparing“, „Background“, „CI of #12“), sind zurückgenommen: grauer Text statt Tag, blasser, langsam pulsierender Punkt. Gilt in der Liste, im Status-Chip der Sitzung und in den Details. In der Liste stehen „Ready“-Sitzungen in einer eigenen Gruppe „Ready“ zwischen „Needs you“ und „Running“; der Filter und die Zahl „Needs you“ (wie das App-Badge) zählen sie nicht mit.
7. **Berechtigungen:** Rückfragen von Claude zu Tool-Freigaben werden im Frontend als Dialog angezeigt und dort bestätigt oder abgelehnt. Der Berechtigungsmodus ist pro Sitzung wählbar.
   - **Umsetzung (entschieden):** Wählbar sind `default` (Fragen), `acceptEdits`, `auto`, `plan`, `dontAsk` und `bypassPermissions` (in der Oberfläche als gefährlich markiert: alles läuft ohne Rückfrage mit allen Rechten des Nutzers). In `auto` entscheidet der Klassifikator von Claude Code über jeden Tool-Aufruf und fragt den Nutzer nur, wenn er unsicher ist. Die App setzt keine eigenen Grenzen: `git push`, `create_pull_request`, `reply_to_review_thread`, `merge_pull_request` (außer bei Automerge, siehe PR-Automatik) und `add_repository` folgen wie jedes Tool dem Modus und den Regeln (auch „für diese Sitzung“ erlaubt). Ein Autofix-Lauf (GitHub-Inhalt als nicht vertrauenswürdiger Kontext) läuft wie jeder Turn im gewählten Modus mit allen Regeln, auch in `auto` und `bypassPermissions`, und darf auch Subagents und Hintergrund-Arbeit starten (Entscheidung 2026-11-20: die Sitzungen arbeiten nur an vertrauenswürdigen Repositories; bis dahin lief er als `default` und jeder Aufruf außer Lesen ging an den Nutzer). Zusätzlich zum Modus bleiben die eigene Freigabe von `git add`/`commit`/`push` des Sitzungs-Branches und `reply_to_review_thread` beim Antworten (beim Auflösen nur nach einem Push in diesem Lauf seit dem letzten Kommentar des Threads, siehe GitHub-Tokens) ohne Rückfrage. Ist der gewählte Modus nicht verfügbar (`auto`: Plan, Modell, Einstellungen; `bypassPermissions`: in den Einstellungen abgeschaltet), läuft Claude Code als `default`; gewählt bleibt der Modus, die Oberfläche zeigt den wirksamen Modus mit Hinweis. Im Plan-Modus kein Klassifikator. Neue Sitzungen starten im Formular mit `auto` vorausgewählt; die API nimmt ohne Angabe weiter `default`.
   - **Umsetzung (entschieden):** Rückfragen von Claude (`AskUserQuestion`) stehen im Verlauf nicht als Tool-Aufruf, sondern als eigene Karte außerhalb der gefalteten Tool-Aufrufe: je Frage Kurzlabel, Frage und die gegebene Antwort (bei gewählten Optionen mit deren Erklärungen), dazu der Stand („Answered“, „Waiting for your answer“, „Not answered: …“, „Cancelled: …“) und ein Fehler des Aufrufs. Ohne lesbare Fragen bleibt es bei der Zeile des Tool-Aufrufs.
8. **Aufräumen der Sitzungsklone:** Nach Abschluss einer Sitzung lassen sich ihre Klone mergen, pushen oder verwerfen, inklusive Diff-Ansicht vorher.

## Architektur

- **Projektstruktur:** Nx-Monorepo mit Angular-Frontend und NestJS-Backend als eigenen Apps sowie gemeinsamen Bibliotheken, etwa für die Typen der Sitzungsereignisse.
- **Backend:** NestJS (Node.js, TypeScript) und dem Claude Agent SDK (`@anthropic-ai/claude-agent-sdk`). Das SDK liefert dieselbe Agent-Schleife wie Claude Code. Das Backend verwaltet Sitzungen, Repositories, Sitzungsklone und den Git-Zugriff.
- **Kommunikation:** REST für Verwaltungsaktionen, WebSocket oder Server-Sent Events für das Streaming der Sitzungsereignisse.
- **Frontend:** Angular-Single-Page-App, responsiv, damit es auch am Handy nutzbar ist.
  - **Umsetzung (entschieden):** „Zurück“ des Browsers (auch die Wischgeste am Handy) führt immer zur Sitzungsliste (Entscheidung 2026-11-20): Unter jeder anderen Seite liegt im Verlauf genau ein Eintrag, die Liste. Von der Liste aus kommen Seiten neu in den Verlauf, zwischen anderen Seiten ersetzen sie den aktuellen Eintrag; der Weg zurück zu genau dieser Liste (Zurück-Pfeil, Logo, Löschen, Archivieren, Weiterleitung unbekannter Seiten) geht zum Eintrag darunter statt eine zweite Liste anzulegen; eine andere Liste (z. B. alle Sitzungen über einer gefilterten) kommt neu dazu. Wird die App direkt auf einer anderen Seite geöffnet (Link, Benachrichtigung, Share Target), legt sie die Liste beim ersten Tippen oder Tastendruck darunter (Chrome überspringt beim Zurück Einträge, die eine Seite ohne Nutzeraktion angelegt hat; wer sofort zurückwischt, verlässt die App). Von der Liste aus verlässt „Zurück“ die App; öffnet eine Benachrichtigung die schon laufende App, lädt sie neu, und unter der neuen Liste bleiben die früheren Einträge.
  - **Umsetzung (entschieden, Styles):** Eigene Styles werden massiv reduziert (Entscheidung 2026-11-20): Layout, Abstände und einfache Gestaltung als Tailwind-Utilities im Template, deren Farben, Radien, Abstände und Schrift aus den Material-Tokens kommen; Bedienelemente bleiben Angular Material. Jede Basiskomponente (Button, Badge, Chip, Fortschrittsbalken, Karte, Banner …) gibt es genau einmal zentral, mit höchstens zwei Varianten, und nur, wenn sich beide sichtbar unterscheiden und gebraucht werden. Komponenten-SCSS nur, wo Utilities nicht reichen (Markdown, Diffs, Diagramme). Umbau in mehreren PRs, jeder mit Vorher/Nachher-Übersicht.
- **Persistenz:** SQLite für Metadaten (Sitzungen, zugehörige Repos und Sitzungsklone, Titel, Zeitstempel). Die eigentlichen Gesprächsverläufe speichert Claude Code selbst.
- **Betrieb:** systemd-Dienst über das NixOS-Modul auf der Devbox, als Benutzer des Besitzers (oder Docker-Container, siehe Laufzeitumgebung), erreichbar über den bestehenden Cloudflare Tunnel mit Google Single Sign-On über Cloudflare Access davor (gilt auch für die Vorschau-Subdomains; nur der GitHub-Webhook-Pfad wird per Bypass-Regel ausgenommen). Keine eigene Anmeldung in der App.
- **Prüfung des Access-Tokens im Backend:** Das Backend verlässt sich nicht allein darauf, dass Cloudflare Access davor sitzt, sondern prüft das Access-JWT jeder Anfrage und jedes WebSocket-Aufbaus selbst (Signatur über die Schlüssel des Teams, Aussteller, Audience der Anwendung, Ablauf; optional eine Liste erlaubter E-Mail-Adressen). Grund: Alles, was den Port des Containers ohne Umweg über Cloudflare erreicht – ein anderer Prozess im Container, der Host, das lokale Netz –, könnte sonst die API bedienen und etwa ohne Freigabe des Nutzers pushen. Ausgenommen sind nur der Health-Check und der Webhook (Signatur). Für die lokale Entwicklung lässt sich die Prüfung ausdrücklich abschalten. Prozesse der Sitzungen dürfen die Verwaltungs-API nicht aufrufen (etwa um ihre eigenen Freigaben zu beantworten): im Container erkennt das Backend sie am eigenen Benutzer, auf der Devbox (Dienst und Sitzungen laufen als derselbe Benutzer) daran, dass das Backend sie gestartet hat (Prozessbaum, cgroup des Dienstes). Andere Programme des Nutzers auf der Maschine und der Tunnel von einem anderen Rechner sind davon nicht betroffen. Das ist eine Schutzmaßnahme gegen Versehen, keine Grenze: Mit den Rechten des Nutzers kann eine Sitzung auch die Datenbank und die Secrets der App lesen (bewusst in Kauf genommen).

## Konzept der Sitzungsklone

- Pro Repository gibt es einen lokalen Spiegel (bare Repository) unter `<workspace>/repos/<owner>/<repo>`. Er wird einmal aus dem Netz geklont und danach nur noch aktualisiert; niemand arbeitet darin.
- Jede Sitzung bekommt pro Repository einen eigenen, vollständigen Klon dieses Spiegels unter `<workspace>/sessions/<sitzungs-slug>/<owner>/<repo>`. Der lokale Klon verlinkt die Git-Objekte per Hardlink (gleiches Dateisystem) und kostet daher kaum Platz und keinen Netzverkehr; `origin` zeigt auf das echte Remote.
- Grund: vollständige Isolation. Refs, Stash, Tags, Konfiguration, Hooks und Index gehören allein dem Klon der Sitzung, sodass parallele Sitzungen im selben Repository sich nie in die Quere kommen; zugleich wird nicht für jede Sitzung erneut aus dem Netz geklont.
- Branch-Namensschema: `claude/<sitzungs-slug>`.
  - **Umsetzung (entschieden):** Der Slug ist das Datum der Erstellung (in der Zeitzone aus `TZ`, ohne oder mit ungültigem `TZ` in UTC) plus ein Zufallsteil (z. B. `2026-11-20-k3x9q2`); er enthält nichts vom Prompt oder Titel, weil Branch und Verzeichnisnamen sonst den Anfang des Prompts zeigen (der Branch auch auf dem Remote).
- **Umsetzung (entschieden):** Aufräumen und Archivieren bieten auch an, die Sitzungs-Branches auf den Remotes zu löschen (auch von Klonen, die schon entfernt sind). Vorausgewählt (nur bei GitHub-Repositories, weil nur dort offene PRs geprüft werden können), wenn dabei nichts verloren geht: alle Commits liegen auf einem anderen Branch oder Tag des Remotes, oder ein gemergter PR hatte genau diesen Commit als Head (Squash/Rebase). Bei einem offenen PR vom Branch oder in den Branch (z. B. einer Sitzung, die auf diesem Branch gestartet wurde) nicht möglich (Löschen würde ihn schließen). Hat der Branch Commits, die sonst nirgends liegen, nur nach ausdrücklicher Bestätigung. Unmittelbar vor dem Löschen wird erneut geprüft; ein Branch, der sich inzwischen bewegt hat, bleibt.
- **Umsetzung (entschieden), Commit-Identität (2026-11-20):** Name und E-Mail, mit denen in den Sitzungsklonen committet wird, kommen aus Umgebungsvariablen der API (`CRM_GIT_AUTHOR_NAME`, `CRM_GIT_AUTHOR_EMAIL`; NixOS `gitAuthor.name`/`gitAuthor.email`), nicht mehr aus der Einstellungsseite: Die zeigt sie nur noch an, `PUT /api/settings` entfällt, ein früher in der Datenbank gespeicherter Wert wird ignoriert. Beide oder keine; ein ungültiger Wert verhindert den Start. Fehlen sie, startet die API trotzdem, aber Sitzungen mit Repositories und neue lokale Projekte werden mit einem Hinweis auf die Variablen abgelehnt. Beim Start bekommen bestehende Klone mit anderer Identität die aktuelle.
- **Umsetzung (entschieden), Server-Karte (2026-11-20):** Status, Version, Commit und Datum der installierten Version stehen direkt in einer Karte „Server“ der Einstellungsseite statt auf einer eigenen Unterseite. Ungetaggte Builds (Version `0.0.0`) zeigen als Version den Image-Tag `sha-<kurzer Commit>`; das Datum (Commit-Zeit) steht als `yyyy-MM-dd HH:mm` in der Zeitzone aus `TZ` (ohne oder mit ungültigem `TZ` in UTC).
- Eine Sitzung kennt alle ihre Klone; beim Aufräumen werden sie gemeinsam behandelt. Verwerfen heißt, das Verzeichnis der Sitzung zu löschen.
- Verwaiste Sitzungsklone (ohne zugehörige Sitzung) werden in der Übersicht markiert.
- **Umsetzung (entschieden):** Aufräumen geht erst, wenn die Sitzung beendet ist (beim Archivieren wird sie dafür beendet); pro Verzeichnis Push des Sitzungs-Branches (Repos mit Remote, nie Force), Fast-Forward des Basis-Branches (lokale Projekte), Verwerfen oder Behalten (Standard). Was verloren ginge (uncommittete Dateien, Commits ohne Remote, Stash-Einträge), wird vorher gezeigt; ein Verzeichnis mit solcher Arbeit wird nur nach ausdrücklicher Bestätigung gelöscht. Danach bleibt die Sitzung lesbar, lässt sich aber nicht fortsetzen. Gelöscht wird nur innerhalb von `sessions/` und `scratch/`, ohne Symlinks zu folgen und ohne die Rechte des Backends (im Container als Sitzungsbenutzer bzw. ohne Capabilities). Verwaiste Verzeichnisse und fehlende Sitzungsverzeichnisse zeigt eine eigene Seite mit Inhalt und Größe; Entfernen nur nach Bestätigung. Das Ergebnis von Aufräumen und Archivieren (je Verzeichnis, was geschah) erscheint als Toast, nicht als Dialog (siehe „Rückmeldungen“ unter „Weitere Sitzungsfunktionen“).

## GitHub-Referenzen im Prompt

Im Eingabefeld lassen sich Issues und Pull Requests wie in GitHub referenzieren.

- **Autovervollständigung:** Bei Eingabe von `#` erscheint eine Auswahl passender Issues und PRs aus den Repos der Sitzung, durchsuchbar nach Nummer und Titel. Andere Repos über `owner/repo#123`.
- **Anzeige:** Referenzen erscheinen im Prompt und im Verlauf als Chip mit Titel, Status (offen, gemerged, geschlossen) und Link; beim Überfahren eine kurze Vorschau.
- **Kontext für Claude:** Beim Absenden hängt das Backend Titel, Beschreibung und auf Wunsch Kommentare bzw. den Diff des PRs als Kontext an.
- **Datenquelle:** GitHub-API über die GitHub App, mit kurzem Cache.
- **Umsetzung (entschieden):** Kommentare und PR-Diff wählt der Nutzer pro Referenz in der Vorschau des Chips (Standard: aus); die Vorschau öffnet beim Überfahren mit der Maus und beim Antippen. Größen sind begrenzt (Beschreibung, die neuesten 50 Kommentare, Diff, Gesamtkontext); Gekürztes wird Claude und dem Nutzer gesagt. Nicht auflösbare Referenzen (nicht gefunden, Rate-Limit, GitHub nicht erreichbar) halten die Nachricht nicht auf: der Chip zeigt es, Claude erfährt, dass der Inhalt fehlt. Der Inhalt aus GitHub gilt als nicht vertrauenswürdig: Er geht als eigene, markierte Nachricht vor der Nachricht des Nutzers an Claude, ohne `@`-Expansion und Slash-Commands, und ist im Verlauf aufklappbar; dieselbe Schnittstelle nutzt die PR-Automatik.
- **Umsetzung (entschieden): mehrere Repos.** In einer Sitzung mit einem GitHub-Repo meint `#12` dieses. Mit mehreren meint `#12` das Repo, in dem es die Nummer gibt; gibt es sie in mehreren, fragt das Eingabefeld statt eines Chips, welches gemeint ist (die Kandidaten mit Titel und Status), und schreibt nach der Wahl `owner/repo#12` in den Text. Bis das geklärt ist (auch solange die Nummer noch nachgeschlagen wird), lässt sich die Nachricht nicht senden. Gibt es die Nummer in keinem Repo oder ist GitHub nicht erreichbar, gilt wie bisher das erste Repo. Die Autovervollständigung fügt bei mehreren Repos immer `owner/repo#12` ein. Chips zeigen bei mehreren Repos `repo#12` statt `#12`, im Eingabefeld und im Verlauf.

## PR-Automatik pro Sitzung

Zu jeder Sitzung mit offenem Pull Request lassen sich Automatiken ein- und ausschalten.

- **Autofix:** Schlägt ein CI-Check fehl oder kommt ein neuer Review-Kommentar, setzt das Backend die Sitzung automatisch mit diesem Kontext fort; Claude behebt das Problem und pusht auf den Sitzungs-Branch.
- **Autoclose:** Wird der PR gemerged oder geschlossen, wird die Sitzung beendet, ihre Dev-Server gestoppt und die Sitzungsklone aufgeräumt.
- **Umsetzung (entschieden, Weckruf nach Merge):** Ohne Autoclose weckt ein Merge oder Schließen eines PRs der Sitzung Claude mit einer Nachricht der App (was passiert ist, beim Merge in welchen Basis-Branch), aber nur, wenn Claudes Turn vorbei ist und es mit `set_waiting_state` „work“ angekündigt hat, selbst weiterzumachen (Entscheidung 2026-11-20). Wartet die Sitzung auf den Nutzer, bleibt es bei der Benachrichtigung; läuft gerade ein Turn (etwa weil Claude selbst gemerged hat), gibt es keinen Weckruf.
- **Automerge:** Ist die CI komplett grün und haben die Code-Reviews keine Befunde mehr, merged die App den PR selbst (oder Claude mit `merge_pull_request`, siehe unten). Befunde arbeitet die Sitzung vorher per Autofix ab, bis keine mehr offen sind; braucht ein Befund eine Entscheidung des Nutzers, wartet Automerge darauf.
- **Ereignisquelle:** GitHub-Webhooks der GitHub App. Der Webhook-Endpunkt muss am SSO vorbei erreichbar sein und prüft die Webhook-Signatur; alternativ regelmäßiges Abfragen per Polling.
- **Grenzen:** Maximale Anzahl automatischer Fix-Versuche pro PR, danach Benachrichtigung statt weiterer Versuche.
- **Umsetzung (entschieden):** Beide Schalter pro PR, Standard aus; Versuchslimit pro PR (Standard 3, einstellbar), gezählt in der Datenbank, zurückgesetzt nur durch den Nutzer. Webhook und Polling sind nur Anlass, den Stand über die API zu lesen. Auslöser sind fehlgeschlagene Checks des aktuellen Head-Commits (ältere Commits und laufende Checks zählen nicht) und neue Reviews, Review-Kommentare und Kommentare im PR von Nutzern mit Schreibrecht (keine Bots außer den vertrauenswürdigen, siehe unten; nicht die App selbst). Was zusammen eintrifft, wird ein Lauf; während die Sitzung arbeitet oder auf den Nutzer wartet, startet kein Lauf, danach wird neu geprüft. Hat Claude mit `set_waiting_state` nur angegeben, dass es von selbst weitermacht (`work`, z. B. „CI von PR #12“), und laufen keine Hintergrund-Tasks, startet der Lauf trotzdem sofort: Claude wartet meist genau auf das, was der Lauf bringt, sonst warteten beide bis zu 30 Minuten aufeinander. Laufen noch Hintergrund-Tasks (z. B. ein Subagent), wartet der Lauf, bis sie fertig sind und Claude ihren Bericht nicht als eigenen Turn aufgenommen hat (kurze Karenzzeit), oder bis „Background“ abläuft. Dasselbe gilt für Automerge und die Bereit-Meldung. Kontext von GitHub (Check-Ausgabe, Log-Auszug, Kommentare) geht nur als nicht vertrauenswürdiger Kontext an Claude. Während Autofix führt die App `git add`, `git commit` und den Push genau des Sitzungs-Branches ohne Rückfrage selbst aus, auch mit `&&` verbunden, wenn der Befehl nichts anderes enthält (Hooks aus, kein Force, keine Tags, nichts Löschendes, kein Amend gepushter Commits, keine Workflow-Änderungen); alles andere bleibt beim Freigabe-Dialog. Mehrere PRs einer Sitzung: Schalter und Zähler pro PR, ein Lauf zur Zeit; Autoclose erst, wenn kein PR der Sitzung mehr offen ist. Klone mit Arbeit, die nicht auf GitHub liegt, bleiben erhalten und lassen sich nach Bestätigung löschen.
- **Umsetzung (entschieden, Bereit zum Mergen):** Bots, die der Betreiber als vertrauenswürdig einträgt (`PR_TRUSTED_BOTS`, NixOS `github.trustedBots`, z. B. ein Review-Bot), zählen wie Nutzer mit Schreibrecht: Ihre Reviews und Kommentare lösen Läufe aus, ihre Approvals zählen. Approvals selbst lösen keinen Lauf aus; ihr Text geht als Kontext mit. Solange weitere Checks des Head-Commits laufen, warten Fehlschläge und neue Kommentare darauf (höchstens 30 Minuten), damit alles ein Lauf wird. Sind alle Checks des Head-Commits erfolgreich fertig (`success`, `neutral` oder `skipped`; abgebrochene zählen nicht) und ist genau dieser Commit approved (und niemand, der zählt, fordert Änderungen an), teilt die App das der Sitzung einmal pro Head-Commit mit, samt neuer Reviews und Kommentare als nicht vertrauenswürdiger Kontext. Diese Meldung zählt nicht als Versuch, außer es kommen Reviews oder Kommentare mit, die Änderungen verlangen könnten. Ist das Limit erreicht, kommt die Meldung nur mit dem Text der Approvals, und für den Rest gilt die übliche Benachrichtigung über das erreichte Limit. Als vertrauenswürdig nur reine Reviewer-Apps eintragen, nicht etwa `github-actions[bot]`: Dessen Text kann von beliebigen Workflows stammen. Claude merged dann, wenn der Nutzer das so angewiesen hat, mit dem App-Tool `merge_pull_request`; es fragt, wie der Berechtigungsmodus sagt (ohne Rückfrage nur bei Automerge, siehe unten). Ist Automerge an, braucht „bereit“ kein Approval (siehe unten); die Meldung sagt dann, dass niemand Änderungen anfordert.
- **Umsetzung (entschieden, Mergekonflikte, 2026-11-21):** Teil von Autofix, kein eigener Schalter. Meldet GitHub für einen PR mit Autofix Mergekonflikte mit dem Basis-Branch (`mergeable: false`, `mergeable_state: dirty`; gelesen mit dem PR selbst; solange GitHub noch rechnet, gilt der Stand als unbekannt, und die App sieht nach 10 Sekunden erneut nach, höchstens dreimal pro Head-Commit; auch ein Entwurf mit Konflikten zählt), startet ein Lauf, der Claude bittet, den Sitzungs-Branch auf das aktuelle `origin/<Basis>` zu rebasen, die Konflikte zu lösen, lokal zu prüfen und mit `git push --force-with-lease` zu pushen; kann Claude einen Konflikt nicht ohne Entscheidung lösen, bricht es den Rebase ab, pusht nichts und erklärt ihn. Nur echte Konflikte, nicht ein PR, der nur hinter dem Basis-Branch liegt. Ein Lauf pro Head-Commit; er zählt als Versuch (Versuchslimit wie sonst), fehlgeschlagene Checks und neue Kommentare des Commits gehen als nicht vertrauenswürdiger Kontext mit, und er wartet nicht auf noch laufende Checks. Den Rebase macht Claude, nicht die App. Während dieses Laufs (von seiner Nachricht bis zum Ende des Turns) führt die App ein `git push --force-with-lease` (ohne Wert, optional mit `--force-if-includes`; kein `-f`/`--force`, kein `+`-Refspec) genau des Sitzungs-Branches der PRs in einem solchen Lauf ohne Rückfrage selbst aus: als Force-Push nur über den Commit, den der Klon zuletzt von GitHub kannte (`origin/<Branch>`), und nur, wenn der Branch dann den Commit des Basis-Branches enthält, den die App direkt vorher von GitHub liest (nicht `origin/<Basis>` des Klons, dessen Refs die Sitzung ändern kann); weichen die Workflow-Dateien des Branches von denen dieses Basis-Commits ab (als Baum verglichen, also auch bei einem Merge-Commit), fragt der Push wie sonst. Die Freigabe gilt nur, solange der Autofix-Turn tatsächlich läuft, nur für `--force-with-lease` (nicht `--force-if-includes` allein) und nur für den Branch des Klons (`HEAD` oder sein Name). Außerhalb dieses Laufs fragt jeder Force-Push wie der Berechtigungsmodus sagt; der Rebase selbst (`git fetch`, `git rebase`, `git rebase --continue`) folgt immer dem Berechtigungsmodus. Ein Commit mit Konflikten ist nie „bereit“: Automerge wartet („merge conflicts with main“) und versucht keinen Merge, den GitHub ablehnen würde.
- **Umsetzung (entschieden, Automerge):** Dritter Schalter pro PR, Standard aus; er schaltet Autofix mit ein, und Autofix aus schaltet ihn mit aus. Die App merged selbst, sobald der Head-Commit „bereit“ ist (alle Checks erfolgreich fertig und mindestens einer gemeldet, niemand, der zählt, fordert Änderungen an; ein Approval ist nicht nötig, Entscheidung 2026-11-20), kein Review-Thread des PRs unaufgelöst ist (auch Hinweise und Threads von Leuten ohne Schreibrecht halten auf; Claude beantwortet behobene Befunde mit `reply_to_review_thread` und löst sie auf, sonst der Reviewer oder der Nutzer), keine neuen Reviews oder Kommentare auf Bearbeitung warten, der PR kein Entwurf ist und die Sitzung auf eine Nachricht wartet (oder nur auf Claudes Angabe `work` ohne laufende Hintergrund-Tasks, wie bei Autofix). Gemerged wird genau der geprüfte Head-Commit, per Rebase, sonst Squash, ein Merge-Commit nur, wenn beides nicht geht (vom Repo nicht erlaubt oder nicht rebasebar). Danach greifen Benachrichtigung und Autoclose wie bei jedem Merge. Bleiben bei bereitem Commit Threads offen, bekommt die Sitzung die Bereit-Meldung mit den offenen Threads (nur die von Leuten, die zählen, als nicht vertrauenswürdiger Kontext; zählt dann als Versuch) und arbeitet sie ab. Bleiben Threads offen, an denen kein Lauf arbeitet (Claude hat sie ohne Rückfrage stehen lassen, oder keiner ist von jemandem, der zählt), erfährt es der Nutzer einmal pro Head-Commit. Braucht ein Befund die Entscheidung des Nutzers (Produkt- oder Design-Entscheidung, Abwägung, Umfang, oder Claude hält ihn für falsch), ruft Claude das App-Tool `request_owner_decision` mit seiner Frage auf (ohne Freigabe, auch im Autofix-Lauf): Automerge der PRs der Sitzung pausiert, der Nutzer wird benachrichtigt (Ereignis „Automerge braucht dich“), und die nächste Nachricht des Nutzers in der Sitzung hebt die Pause auf (jede, auch eine, die er vor dem Lesen der Frage schickt). Claude darf selbst mergen (Entscheidung 2026-11-20): `merge_pull_request` läuft bei Automerge ohne Rückfrage (vor Modus und Regeln), wenn der PR in diesem Moment bereit ist wie oben, frisch von GitHub gelesen (offen, kein Entwurf, Automerge nicht pausiert, alle Checks des Head-Commits erfolgreich und mindestens einer gemeldet, niemand, der zählt, fordert Änderungen an, keine neuen Reviews oder Kommentare seit dem letzten Lauf, kein Review-Thread offen), und merged genau den geprüften Head-Commit, nachdem es unmittelbar davor erneut geprüft hat; sonst fragt es, wie der Berechtigungsmodus sagt (im Plan-Modus nie ohne Rückfrage). Rückmeldungen, die schon an einen laufenden Autofix-Lauf gingen, halten nicht mehr auf, wie beim Automerge der App nach dem Lauf. Autoclose nach einem Merge (auch einem auf GitHub) wartet, bis der Turn der Sitzung vorbei ist (nicht, solange eine Freigabe offen ist), damit Claudes eigener Merge nicht den laufenden Turn beendet; nach einem Neustart holt die erste Abfrage das nach. Threads beantwortet und löst Claude nur über `reply_to_review_thread`: behobene mit dem, was sich geändert hat (Commit), und aufgelöst, nicht behobene mit der Begründung und offen gelassen; Threads von Leuten, die nicht zählen, gar nicht. Vorübergehende Ablehnungen (Basis-Branch bewegt, Mergebarkeit noch nicht berechnet, GitHub nicht erreichbar) werden bis zu dreimal wiederholt. Verweigert GitHub den Merge weiter (Konflikt, Branch-Schutz, Workflow-Dateien ohne Berechtigung), erfährt es der Nutzer einmal pro Head-Commit; erneut versucht wird mit dem nächsten Head-Commit oder nach Aus- und Einschalten. Bekannte Grenze (entschieden, vorerst so): Wo Branch Protection Reviews verlangt, zählt auch das Approval des Nutzers; da Sitzungen als sein Nutzer mit seinen GitHub-Zugangsdaten laufen, könnte Claude in jedem Turn (seit 2026-11-20 auch im Autofix-Lauf) selbst approven oder Threads auflösen. Dass Claude das nicht tut, ist nur Anweisung, nicht erzwungen; dokumentiert statt verhindert.

## Unabhängiges Review

Ein zweites Modell prüft die Änderungen einer Sitzung, ohne die Schlussfolgerungen des Hauptagenten zu kennen, und gibt die Befunde dem Hauptagenten zum Beheben.

- **Umsetzung (entschieden, 2026-11-23):** Den Reviewer startet die App als eigenen Claude-Code-Prozess, nicht der Hauptagent als Subagent: nur mit Lesezugriff (`Read`, `Grep`, `Glob`, nur in den Verzeichnissen der Sitzung; sonst keine Tools, keine MCP-Server, keine Hooks), in den Klonen der Sitzung, ohne gespeichertes Transkript, mit eigenem Modell und Effort. Er bekommt den Diff der Sitzung (alle Klone gegen ihren Basis-Branch wie die Diff-Ansicht, mit nicht committeten und neuen Dateien) und neutrale Anweisungen, nichts aus dem Gespräch der Sitzung, und liefert seine Befunde strukturiert (Schwere, Datei, Zeile, Titel, Begründung). Die CLAUDE.md-Dateien des Projekts gelten auch für ihn.
- **Umsetzung (entschieden):** Modell und Effort stellt der Nutzer global in den Einstellungen ein (Standard Fable 5.2, Effort High) und pro Sitzung abweichend (Standard: der globale Wert). Ebenfalls global: das Rundenlimit des Auto-Reviews (Standard 3).
- **Umsetzung (entschieden):** Ein Knopf „Review“ der Sitzung startet ein Review sofort, auch während Claude arbeitet (geprüft wird der Stand beim Start); höchstens eines pro Sitzung läuft gleichzeitig, es lässt sich abbrechen und wird nach 30 Minuten abgebrochen; Archivieren der Sitzung bricht es ebenfalls ab. Ohne Änderungen gibt es nichts zu prüfen.
- **Umsetzung (entschieden):** Die Befunde gehen sofort und ohne Rückfrage als Nachricht der App an den Hauptagenten (läuft gerade ein Turn, eingereiht); er behebt sie oder begründet, warum nicht. Die Befunde selbst gehen als nicht vertrauenswürdiger Kontext mit (der Reviewer hat Inhalte des Repositorys gelesen). Im Verlauf zeigt eine Karte das Review: läuft, Befunde, Fehler oder abgebrochen, mit Modell, Effort, Dauer und Kosten. Ohne Befunde geht keine Nachricht an Claude. Einer archivierten Sitzung schickt die App die Befunde nie; einer inzwischen beendeten nur die eines vom Nutzer gestarteten Reviews (das setzt sie fort), die eines Auto-Reviews nicht. Der Verbrauch des Reviewers zählt zur Sitzung.
- **Umsetzung (entschieden):** Auto-Review ist ein Schalter pro Sitzung, Standard aus. Ist er an, startet ein Review, sobald ein Turn endet (die Sitzung wartet auf eine Nachricht oder nur auf das, womit Claude selbst weitermacht) und sich der Inhalt des Diffs der Sitzung seit dem letzten Review geändert hat (nur Committen oder Rebasen zählt nicht; endet ein Turn, während ein Review läuft, prüft die App nach dessen Ende), auch nach den Turns, die Befunde beheben. Runden mit Befunden werden gezählt; ist das Limit erreicht, startet kein Auto-Review mehr und eine Notiz im Verlauf sagt es, bis der Nutzer eine Nachricht schreibt (das setzt den Zähler zurück, ebenso ein Review ohne Befunde). Solange ein Review läuft (bis seine Befunde zugestellt sind), startet die PR-Automatik nichts und merged nicht, und `merge_pull_request` fragt, wie der Modus sagt.

## Benachrichtigungen

Sitzungen arbeiten meist unbeobachtet, daher meldet das Backend wichtige Ereignisse aktiv. Beide Kanäle werden unterstützt und sind einzeln schaltbar.

- **Web Push:** Das Angular-Frontend ist eine PWA mit Service Worker; Push über Web Push mit VAPID-Schlüsseln. Auf iOS nur, wenn die App zum Home-Bildschirm hinzugefügt ist.
- **ntfy:** Das Backend sendet zusätzlich an einen konfigurierbaren ntfy-Server und -Topic und authentifiziert sich dabei mit einem Access-Token (Bearer-Header). Der Token ist Pflicht und wird als Secret übergeben, nicht im Image oder in der Datenbank im Klartext.
- **Ereignisse:** Claude wartet auf eine Freigabe, Sitzung ist fertig oder hängt, Autofix gibt nach dem Versuchslimit auf, Automerge wartet auf eine Entscheidung, hängt an offenen Threads oder GitHub verweigert den Merge, PR wurde gemerged oder geschlossen.
- **Ziel:** Ein Tipp auf die Benachrichtigung öffnet direkt die betreffende Sitzung (für ntfy-Links über die öffentliche URL der App, `PUBLIC_URL`).
- **Einstellungen:** Pro Ereignistyp und Kanal ein- und ausschaltbar.
- **Festlegungen:** „Fertig“ heißt: ein Turn ist zu Ende und Claude wartet auf die nächste Nachricht (das ausdrückliche Beenden einer Sitzung meldet nichts); laufen danach noch Hintergrund-Tasks von Claude, wird „fertig“ erst gemeldet, wenn keine mehr laufen und Claude danach nicht von selbst weitermacht (die Sitzung bleibt dafür bis zu 30 Sekunden auf „Background“; endet der Prozess mit noch laufenden Tasks, steht ein Hinweis im Verlauf) (Umsetzung (entschieden)). „Hängt“ heißt: Status `running` und seit `SESSION_STALL_MINUTES` (Standard 15) kein Ereignis von Claude; einmal pro Hänger, erneut erst nach neuer Aktivität. Eine fehlgeschlagene Sitzung (auch ein fehlgeschlagenes Setup-Skript) meldet sofort. Rückfragen von Claude melden wie Freigaben, ohne Erlauben/Ablehnen. Inhalt: Sitzungstitel, Repositories, bei Freigaben Aktion mit gekürztem Befehl oder Dateipfad.
- **Nur was aktuell ist:** Zu einer Sitzung, die ein Client gerade sichtbar und aktiv zeigt, wird nichts gemeldet. Nicht mehr aktuelle Benachrichtigungen werden zurückgezogen (Web Push: per Tag geschlossen, außer auf Apple-Geräten; ntfy: per Sequenz-ID gelöscht).

## PWA-Funktionen

Das Angular-Frontend nutzt als installierbare PWA zusätzlich:

- **Aktionen in Benachrichtigungen:** Freigabe-Anfragen lassen sich direkt in der Push-Nachricht mit „Erlauben“ oder „Ablehnen“ beantworten, ohne die App zu öffnen. „Erlauben“ heißt einmal erlauben (nie für die ganze Sitzung, kein Moduswechsel); Pushes, die mehr als den Sitzungs-Branch ändern, bekommen kein „Erlauben“. Kommt die Antwort nicht an (Access abgelaufen, offline), öffnet sich die Sitzung mit der weiter offenen Anfrage.
- **Badge am App-Icon:** Badging API zeigt die Zahl der Sitzungen, die auf den Nutzer warten: offene Freigabe, Rückfrage oder Plan, oder ein fehlgeschlagenes Setup-Skript, das die erste Nachricht zurückhält; eine Sitzung, deren Turn fertig ist und die nur auf die nächste Nachricht wartet, zählt nicht. „Wartende Sitzungen“ zeigt genau diese.
- **Share Target:** Links, Screenshots oder Text aus anderen Apps lassen sich an die PWA teilen und werden zum Prompt einer neuen Sitzung (das Formular wird vorausgefüllt; der Service Worker nimmt den Upload selbst entgegen, die API bleibt bei JSON).
- **App-Shortcuts:** Langes Drücken auf das Icon bietet „Neue Sitzung“ und „Wartende Sitzungen“.
- **Offline-Shell:** Die App startet sofort und zeigt den zuletzt bekannten Stand der Sitzungsliste, auch bei kurzer Verbindungsunterbrechung.
- **Hinweis Cloudflare Access:** Läuft die Access-Sitzung ab, kann die installierte PWA auf der Login-Seite hängen bleiben. Lange Sitzungsdauer in Access wählen und abgelaufene Anmeldung im Frontend erkennen und sauber zur Neuanmeldung führen.

Titel in der Sprache des Gesprächs, etwa drei bis sechs Wörter. Jede Änderung erscheint als kleine Zeile im Verlauf.

Ein Toast ohne Fehler verschwindet nach einigen Sekunden (länger bei mehr Zeilen, nicht solange Zeiger oder Fokus darauf sind); einer mit Fehler bleibt, bis er weggeklickt wird, und wird als Warnung vorgelesen. Fehler, die eine Entscheidung im offenen Dialog brauchen, bleiben im Dialog. Auch Aktionen, die sonst still endeten, melden sich so: Klon verwerfen, Sitzung löschen, Sitzung wieder einblenden (Archivierung aufheben), verwaistes Verzeichnis entfernen, fehlendes Verzeichnis als entfernt markieren, Setup-Skript speichern oder entfernen, Gerät aus Web Push entfernen.

## Environments

Wie die Environments von Claude Code im Web, aber freier: Ein Environment bündelt, was Sitzungen für eine Art von Arbeit brauchen, vor allem Secrets beliebiger Art (nicht nur Bearer-Tokens), und wird beim Start einer Sitzung gewählt.

- **Inhalt:** Name; Zusatzinfos (Freitext, der an den System-Prompt der Sitzung angehängt wird, wie die globale Anweisungsdatei, z. B. „Die Staging-API liegt unter …, der Key steht in `$STAGING_KEY`“); Variablen; Secret-Dateien; ein Setup-Skript; Vorgaben für Repositories (Haupt- und weitere, mit Basis-Branch), Modell und Berechtigungsmodus.
- **Umsetzung (entschieden), Variablen:** Beliebige `NAME=Wert`-Paare als Umgebungsvariablen des Claude-Code-Prozesses (und damit aller Befehle) und der Setup-Skripte. Pro Variable ein Schalter „Secret“: an heißt verschlüsselt gespeichert, nach dem Speichern nicht mehr lesbar (nur ersetzen oder löschen, wie Secrets in GitHub Actions) und im Verlauf maskiert; aus heißt Klartext, sicht- und editierbar (z. B. `API_BASE_URL`). Namen wie in der Shell (`[A-Za-z_][A-Za-z0-9_]*`); Namen, die die App oder Claude Code selbst brauchen (u. a. `PATH`, `HOME`, `USER`, `SHELL`, `NODE_OPTIONS`, `LD_PRELOAD`, `BASH_ENV`, `GH_TOKEN`, `GITHUB_TOKEN`, `CLAUDE_*`, `ANTHROPIC_*`, `CRM_*`, `GIT_CONFIG_*`), werden abgelehnt, damit ein Environment weder die Sitzung noch die Anmeldung von Claude Code umbiegt. `GH_TOKEN` und `GITHUB_TOKEN` sind gesperrt (Entscheidung 2026-11-19), damit kein eigener Token je nach Sitzung das nur lesende `gh`-Token ersetzt und damit die Garantie aufhebt, dass Sitzungen nicht freigeben oder an den App-Tools vorbei mergen; ein Token unter anderem Namen (z. B. `GITHUB_PAT`) lässt sich bewusst übergeben.
- **Umsetzung (entschieden), Secret-Dateien:** Dateien mit Name und Inhalt (z. B. Service-Account-JSON, kubeconfig, `.npmrc`), ebenfalls mit Schalter „Secret“. Sie liegen nicht im Home und nicht in den Klonen, sondern in einem eigenen Verzeichnis pro Sitzung und Prozess außerhalb der Klone (nur für den Sitzungsbenutzer lesbar, `0600`), und ihr Pfad kommt in eine Variable, die der Nutzer pro Datei angibt (z. B. `GOOGLE_APPLICATION_CREDENTIALS`, `KUBECONFIG`, `NPM_CONFIG_USERCONFIG`). So überschneiden sich parallele Sitzungen mit verschiedenen Environments nicht. Die Dateien werden vor dem Start des Claude-Code-Prozesses bzw. eines Setup-Skripts geschrieben und an dessen Ende gelöscht.
- **Umsetzung (entschieden), Schutz:** Secrets (Variablen und Dateien) liegen in SQLite mit AES-256-GCM verschlüsselt; der Schlüssel kommt aus einem App-Secret (Datei `ENVIRONMENT_KEY_FILE` oder Variable `CRM_SECRET_ENVIRONMENT_KEY`, 32 Byte als Base64 oder Hex), sonst erzeugt die App ihn beim ersten Bedarf als Datei im Datenbankverzeichnis (`0600`). Die API gibt Secret-Werte nie heraus, auch nicht an die Oberfläche. Tauchen Secret-Werte (ab 6 Zeichen; bei Dateien der ganze Inhalt, die Werte darin – JSON-Werte, `KEY=Wert`, `key: Wert` – und lange Zeilen ohne Leerzeichen wie der Körper eines PEM-Schlüssels, nicht aber gewöhnliche Zeilen) in Ereignissen der Sitzung auf (Text, Tool-Eingaben und -Ausgaben, Setup-Ausgaben, Fehler und `lastError`, von Claude gesetzte Titel; gestreamter Text und die Ausgabe der Setup-Skripte werden zurückgehalten, bis sie nicht mehr Teil eines einzeiligen Secrets werden können (so viele Zeichen wie das längste einzeilige Secret); mehrzeilige Secrets wie ganze Dateien werden im Stream über ihre Werte und langen Zeilen maskiert, im fertigen Text auch als Ganzes), speichert und zeigt die App sie als `***` (mit den jeweils aktuellen Werten, auch beim Laden älterer Verläufe), damit auch Benachrichtigungen und Suche sie nicht enthalten. Grenzen: Claude selbst kennt die Werte und kann sie ausgeben oder in Dateien schreiben; Diffs, Dateibrowser und gezeigte Dateien zeigen Dateien so, wie sie auf der Platte liegen; das Transkript von Claude Code enthält die Werte.
- **Umsetzung (entschieden), Zuordnung:** Die Auswahl steht im Formular „Neue Sitzung“ (optional; ein Environment lässt sich als Standard markieren und ist dann vorgewählt) und gilt für die ganze Sitzung, ohne späteren Wechsel. Die Wahl übernimmt die Vorgaben des Environments ins Formular (Repositories, Modell, Modus), die sich dort noch ändern lassen. Variablen, Dateien, Zusatzinfos und Setup-Skript werden bei jedem Start eines Claude-Code-Prozesses der Sitzung frisch gelesen: Ein geänderter Key wirkt beim nächsten Prozessstart. Die Sitzungsdetails zeigen das Environment. Autofix-Läufe bekommen die Secrets wie jeder andere Lauf.
- **Umsetzung (entschieden), Setup-Skript:** Läuft nach den Setup-Skripten der Repositories einmal beim Vorbereiten der Sitzung, im Arbeitsverzeichnis (Haupt-Klon oder Scratch-Verzeichnis), mit den Variablen und Dateien des Environments; Ausgabe, Fehlschlag und „erneut versuchen“ wie bei den Setup-Skripten der Repositories. Lassen sich Variablen oder Dateien nicht vorbereiten (z. B. geänderter Schlüssel), schlägt nur das Setup des Environments fehl; die Skripte der Repositories laufen ohne sie.
- **Umsetzung (entschieden), Löschen:** Ein Environment lässt sich erst löschen, wenn keine Sitzung es mehr nutzt, auch keine archivierte (Entscheidung 2026-11-20): Ihr Verlauf enthält die Secrets, und maskiert werden sie nur, solange das Environment besteht. Der Dialog nennt die Sitzungen; sie müssen erst endgültig gelöscht werden.
- **Verwaltung:** Eigene Seite „Environments“ (Liste, Anlegen, Bearbeiten, Löschen). Secret-Felder zeigen nur „gesetzt“ mit „Ersetzen“ und „Löschen“.

## Anzeige von Kontext- und Abo-Limits

Die Oberfläche zeigt jederzeit, wie viel Spielraum noch bleibt. Drei Werte sind sichtbar:

- **Kontextlimit:** Auslastung des Kontextfensters der jeweiligen Sitzung (belegte und maximale Tokens, Prozent), live in der Sitzungsansicht.
- **Session-Limit:** Verbrauch im aktuellen 5-Stunden-Fenster des Abos, mit Prozentwert und Zeitpunkt des Zurücksetzens.
- **Wochenlimit:** Verbrauch im aktuellen Wochenfenster des Abos, mit Prozentwert und Zeitpunkt des Zurücksetzens; falls das Abo getrennte Wochenlimits pro Modell ausweist, werden diese einzeln angezeigt.

Session- und Wochenlimit gelten für das ganze Konto und sind deshalb global sichtbar (z. B. in der Kopfzeile bzw. Sitzungsliste), nicht nur innerhalb einer Sitzung. Die Werte stammen aus den Limit-Informationen, die Claude Code bzw. das Agent SDK liefert, und werden bei jeder Anfrage aktualisiert.

### Fortsetzen nach dem Abo-Limit

Beendet das Session- oder Wochenlimit des Abos einen Turn, erkennt die App das und setzt die Sitzung nach dem Zurücksetzen des Limits von selbst fort.

- **Umsetzung (entschieden, 2026-11-21):** Gilt immer, für alle Sitzungen, für das 5-Stunden- wie für das Wochenlimit. Mehrere unterbrochene Sitzungen laufen nach dem Zurücksetzen alle sofort weiter (keine Staffelung). Nachrichten, die der Nutzer währenddessen schickt, werden bis zum Zurücksetzen zurückgehalten (in der Warteschlange, entfernbar, „Jetzt senden“ schickt sie sofort) und gehen dann statt der Fortsetzungs-Nachricht der App an Claude.
- **Umsetzung (entschieden, 2026-11-21), Autofix:** Ein unterbrochener Autofix-Lauf geht als Autofix weiter, ohne weiteren Versuch zu zählen, sofern Autofix für den Pull Request dann noch an und er offen ist; sonst als gewöhnlicher Turn. Hat der Nutzer währenddessen Nachrichten geschickt, gehen diese statt der Fortsetzung an Claude, und der Autofix-Lauf endet damit.
- **Erkennung:** Claude Codes Fehler `rate_limit` beendet den Turn; das zugehörige Limit-Ereignis nennt Fenster und Zeitpunkt des Zurücksetzens. Die Sitzung zeigt „Usage limit · 01:31“ und ein Banner mit „Continue now“ und „Don't continue“; die Benachrichtigung zum Turn sagt, wann es weitergeht.
- **Zurückgesetzt?** Eine Minute nach dem Zurücksetzen liest die App die Limits neu; ist ein Fenster noch erschöpft, wartet sie auf dessen neues Zurücksetzen. Ist der Zeitpunkt unbekannt, sieht sie nach 5 Minuten nach (nach einem erneut gescheiterten Fortsetzen oder wenn die Limits nicht lesbar sind, nach 30 Minuten). Der Wartezustand übersteht Neustarts; zurückgehaltene Nachrichten nicht (sie werden wie die Warteschlange beim Stopp des Servers zurückgezogen).
- **Fortsetzungs-Nachricht:** Ohne zurückgehaltene Nachrichten sagt die App Claude, dass das Limit den letzten Turn beendet hat und zurückgesetzt ist, es dort weitermachen soll und Hintergrund-Tasks dieses Turns erst prüfen soll.

## Dateien zeigen

Claude kann dem Nutzer von sich aus eine Datei zeigen, etwa einen erzeugten Screenshot, ein Bild, einen Bericht oder eine HTML-Seite. Gemeint ist ausdrücklich kein allgemeiner Dateibrowser, sondern dass Claude eine bestimmte Datei gezielt vorlegt.

- **Tool:** Das Backend stellt Claude über das SDK ein eigenes Tool `show_file` (Pfad, optionale Bildunterschrift) bereit. Erlaubt sind nur Dateien aus den Verzeichnissen der Sitzung.
- **Anzeige:** Die Datei erscheint als Karte im Verlauf und lässt sich in einer Seitenansicht öffnen: Bilder direkt, Markdown und HTML gerendert, Code und Text mit Syntax-Highlighting, PDF eingebettet; alles andere als Download.
- **Bilder im Verlauf:** Bilder, die Claude zeigt, erzeugt oder liest, erscheinen als Miniatur direkt im Chat, ohne Klick.
- **Stand der Datei:** Gezeigt wird der Inhalt zum Zeitpunkt des Zeigens; er bleibt im Verlauf sichtbar, auch wenn die Datei später geändert oder die Sitzung aufgeräumt wird.
- **Benachrichtigung:** Gezeigte Dateien lösen keine eigene Benachrichtigung aus.

## Statistik und Kosten

Das Backend protokolliert den Verbrauch jeder Sitzung und zeigt ihn im Frontend über die Zeit an.

- **Erfassung:** Aus den Ergebnis-Nachrichten des Agent SDK pro Anfrage die Token-Zahlen (Eingabe, Ausgabe, Cache-Schreiben, Cache-Lesen), das Modell und die vom SDK berechneten theoretischen Kosten in USD; gespeichert in SQLite.
- **Theoretische API-Kosten:** Was die Nutzung bei Abrechnung über die API gekostet hätte, obwohl über das Abo gearbeitet wird.
- **Auswertung:** Verbrauch und Kosten über die Zeit (Tag, Woche, Monat) als Diagramm, aufgeteilt nach Sitzung, Repository und Modell.
- **Pro Sitzung:** Summe von Tokens und theoretischen Kosten direkt in der Sitzungsansicht.
- **Umsetzung (entschieden):** Tages-, Wochen- (Montag bis Sonntag) und Monatsgrenzen in der Zeitzone des Browsers. Eine Sitzung mit mehreren Repositories zählt einmal unter allen zusammen (z. B. `acme/app + acme/lib`), damit die Gruppen die Summe ergeben. Unterbrochene Anfragen fehlen in den Zahlen des SDK; sie werden nicht geschätzt.

## Vorschau von Dev-Servern

Claude kann in einer Sitzung Dev-Server starten, die das Backend als Vorschau ins Frontend durchreicht.

- **Start:** Claude startet den Dev-Server als Hintergrundprozess im Container, im Klon der Sitzung.
- **Port melden:** Das Backend stellt Claude über das SDK ein eigenes Tool `expose_port` (Port, Name) bereit. Optional erkennt das Backend zusätzlich neu lauschende Ports der Sitzung automatisch.
- **Weiterleitung:** NestJS leitet als Reverse Proxy weiter, inklusive WebSockets für Hot Reload.
- **Adressen:** Eigene Subdomain pro Vorschau, z. B. `<sitzung>-<port>.preview.<domain>`, statt Unterpfaden (vermeidet Probleme mit Asset-Pfaden und Hot Reload). Dazu ein Wildcard-Eintrag im Cloudflare Tunnel; die Vorschau liegt ebenfalls hinter SSO.
- **Frontend:** Laufende Vorschauen erscheinen in der Sitzung als Link und optional als eingebettete Ansicht.
- **Aufräumen:** Beim Beenden oder Aufräumen einer Sitzung werden ihre Dev-Server gestoppt und die Weiterleitungen entfernt.
- **Umsetzung (entschieden):** `expose_port` braucht keine Freigabe; Claude kann eine Vorschau mit `stop_preview` beenden, der Nutzer per Knopf. Weitergeleitet werden nur Ports, auf denen ein Prozess des Sitzungsbenutzers auf Loopback lauscht (nie der Port der App), geprüft bei jeder Verbindung. Der Dev-Server sieht die Anfragen wie lokal (`Host`/`Origin` `localhost:<port>`), ohne Access-Token, Cloudflare- und Weiterleitungs-Header. Vorschau-Hosts liefern nichts von der App, der App-Host keine Vorschau; mit Cloudflare Access haben die Vorschauen eine eigene Access-Anwendung mit eigener Audience, deren Token die API nicht annimmt. Die eingebettete Ansicht ist ein Frame mit `sandbox` ohne Top-Navigation. „Stopp“ beendet nur die Weiterleitung; beim Ende der Sitzung werden auch die Prozesse hinter ihren Ports beendet (läuft alles als ein Benutzer, nur die, die das Backend gestartet hat). Keine automatische Erkennung neuer Ports: Alle Sitzungen laufen als derselbe Benutzer, ein Port lässt sich keiner Sitzung sicher zuordnen.

## Laufzeitumgebung und Container

Zwei Wege, beide gebaut und getestet:

- **Umsetzung (entschieden), Umzug in den Container (2026-11-19):** Der Claude Remote Manager zieht als Docker-Container (Compose-Stack) auf den Heimserver und ist damit von der Devbox abgeschottet; er dient nur noch der Anwendungsentwicklung über GitHub. Zugriff aufs Heimnetz, auf die Devbox, ihr `~/.claude`, Docker und `sudo` entfällt bewusst (dafür gibt es Claude Desktop und RDP auf der Devbox). Der Container ist damit der Hauptweg; der NixOS-Dienst wird nach dem Umzug aus dem Repository entfernt. Sitzungen auf der Devbox werden nicht übernommen: Der Server fängt mit neuer Datenbank und neuem Arbeitsbereich an.

- **NixOS-Dienst (bisher Hauptweg, Devbox; entfällt nach dem Umzug):** Das NixOS-Modul startet Backend, Frontend und die Claude-Code-Prozesse als systemd-Dienst des Benutzers, den die Konfiguration nennt (`services.claude-remote-manager.user`, auf der Devbox der Login-Benutzer des Besitzers).
  - **Umsetzung (entschieden):** Keine Sandbox und keine Trennung von Dienst- und Sitzungsbenutzer: keine systemd-Härtung (`ProtectSystem`, `ProtectHome`, `PrivateTmp`, `PrivateDevices`, `NoNewPrivileges`, Syscall-Filter, versteckte Pfade), keine Capabilities. Sitzungen nutzen das `~/.claude` des Benutzers (kein eigenes `CLAUDE_CONFIG_DIR`; Einstellungen, Skills, Plugins, MCP-Server und claude.ai-Connectors wie im Terminal), seine Git-Konfiguration, `gh` und SSH-Schlüssel, `sudo`, Geräte und Docker; der `PATH` ist der einer Login-Shell des Benutzers (`/run/wrappers/bin` zuerst). Die Secrets der App (GitHub-App-Schlüssel, ntfy-Token, Datenbank) kommen als systemd-Credentials und sind für Sitzungen lesbar; das ist in Kauf genommen. Die eigenen Git-Befehle des Backends auf den Spiegeln nutzen Installation-Tokens und eine eigene Git-Konfiguration (`API_GIT_CONFIG_GLOBAL`), damit Einstellungen des Nutzers (URL-Umschreibungen, Signieren) sie nicht ändern. Anweisungen für alle Sitzungen dieser Maschine (Verzeichnisse, NixOS, `extraInstructions`) hängt das Backend an den System-Prompt an, statt eine maschinenweite `/etc/claude-code/CLAUDE.md` zu schreiben, die auch die Terminal-Sitzungen des Nutzers laden würden.
  - **Umsetzung (entschieden), Umstieg von der Version mit getrennten Benutzern:** Der Dienst übergibt das Datenverzeichnis beim ersten Start einmal rekursiv an den Benutzer (eine Stempeldatei merkt sich, an wen). Die Transkripte alter Sitzungen liegen im alten Konfigurationsverzeichnis `<dataDir>/claude`; das Backend kopiert beim Start einmal alles aus dessen `projects/`, was in `~/.claude/projects/` fehlt (die Projektnamen sind die unveränderten Klonpfade), und verschiebt das Repository-Memory nach `<dataDir>/memory`, damit alte Sitzungen fortgesetzt werden können. Nichts wird überschrieben oder gelöscht; eine Markierungsdatei verhindert eine Wiederholung. Den alten Login übernimmt es nicht. Den alten Credential-Helper der App entfernt es aus einem Klon beim nächsten Start eines Claude-Code-Prozesses der Sitzung.
- **Docker-Container:** NestJS-Backend, ausgeliefertes Angular-Frontend und die Claude-Code-Prozesse in einem Container.
  - **Image unabhängig vom Host:** normales Dockerfile, keine Annahmen über NixOS auf dem Host. Das Image muss auf jedem Docker-Host laufen.
  - **Nix im Container:** Im Image ist Nix (Single-User, Flakes aktiviert) installiert. Repositories bringen ihre Werkzeuge über eine eigene `flake.nix` mit Dev-Shell mit; Claude führt Builds und Tests in dieser Umgebung aus (z. B. über `nix develop` oder direnv).
  - **Fallback:** Repos ohne Flake starten mit einer kleinen Grundausstattung im Image (git, Node.js). Fehlende Werkzeuge holt sich Claude bei Bedarf selbst über Nix, z. B. mit `nix shell nixpkgs#dotnet-sdk`.
  - **Volumes:** Arbeitsbereich mit Spiegeln, Sitzungsklonen und Scratch-Verzeichnissen (ein Volume, damit Hardlinks möglich sind), das Claude-Verzeichnis (Login, Sitzungsverläufe), SSH-Key bzw. Git-Zugangsdaten, SQLite-Datenbank sowie der Nix-Store als Cache, damit Werkzeuge nicht bei jedem Neustart neu geladen werden.
  - **Benutzer:** Im Container laufen Backend und Sitzungen weiterhin als getrennte Benutzer; die Sitzungen erreichen die Daten der App nicht. Eigene Zugangsdaten (SSH-Schlüssel, Token) hat der Sitzungsbenutzer nicht.
  - **Umsetzung (entschieden), GitHub-Tokens für Sitzungen im Container (2026-11-19):** `git` und `gh` der Sitzungen bekommen kurzlebige Installation-Tokens der GitHub App vom Backend, über einen Helper, der sich mit einem Prozess-Token der Sitzung ausweist (nur von Sitzungsprozessen aufrufbar, beim Ende des Prozesses widerrufen). `git`: nur das Repository des Remotes, das ein Klon der Sitzung sein muss, mit `contents: write` (bei Änderungen an Workflow-Dateien zusätzlich `workflows: write`); ob ein `git push` läuft, entscheidet wie bei jedem Befehl der Berechtigungsmodus der Sitzung, ohne eigene Freigabe des Helpers. `gh`: alle Repositories der Sitzung derselben Installation, nur lesend (PRs, Reviews, Issues, Checks, Actions); Kommentieren, Approven, Mergen und Auflösen von Review-Threads gehen damit nicht. Das `git`-Token kann allerdings über die API mergen und auf jeden Branch pushen; die Automerge-Grenze hält deshalb nur zusammen mit Branch Protection auf GitHub. Da alle Sitzungen als ein Benutzer laufen, kann eine Sitzung das Prozess-Token einer anderen laufenden Sitzung lesen; die Grenze ist „Repositories der laufenden Sitzungen“. Ein SSH-Schlüssel ist dafür nicht nötig.
  - **Umsetzung (entschieden), Review-Threads (2026-11-20):** Claude kann über das App-Tool `reply_to_review_thread` auf Review-Threads der PRs der eigenen Sitzung antworten und sie auflösen (Repository, PR-Nummer, REST-ID eines beliebigen Review-Kommentars des Threads, Antwort in Markdown und/oder Auflösen); das Backend führt es mit einem Installation-Token (`pull_requests: write`) nur für dieses Repository aus (Antwort über REST, Auflösen über GraphQL `resolveReviewThread`), PRs, die nicht zur Sitzung gehören, lehnt es ab; `gh` bleibt nur lesend. Es fragt, wie der Berechtigungsmodus sagt (der Dialog zeigt PR, Kommentar, Antwort und ob aufgelöst wird); während Autofix zusätzlich Antworten ohne Rückfrage, Auflösen ohne Rückfrage nur, wenn in diesem Autofix-Lauf nach dem letzten Kommentar des Threads ein Push auf den PR-Branch kam (der PR-Head ist). Geprüft wird mit Daten von GitHub (nie mit dem Klon): der aktuelle Head-Commit des PRs muss der des letzten Pushs auf den Branch laut Repository-Aktivität von GitHub sein (Token mit `contents: read`), dieser Push muss nach dem Start des Laufs und nach dem letzten Kommentar des Threads liegen, der nicht von der App selbst stammt (je Kommentar das späteste von erstellt, veröffentlicht – ein Review-Kommentar erst mit dem Absenden des Reviews – und zuletzt bearbeitet); unvollständige Angaben zählen als nicht erfüllt. Unmittelbar vor dem Auflösen prüft das Tool erneut (kein neuerer Kommentar, derselbe Head); hält es nicht mehr, antwortet es nur und lässt den Thread offen. Das ist ein Push seit dem Kommentar in diesem Lauf, kein Beweis, dass der Befund behoben ist. Sonst, und wenn die Prüfung scheitert, entscheidet der Berechtigungsmodus (in `dontAsk`-Sitzungen fragt Claude Code niemanden und lehnt es wie jede nicht vorab erlaubte Aktion ab, wie auch die Autofix-Freigabe von `git add`/`commit`/`push`). Der Autofix-Kontext nennt dafür die `comment-id` jedes Review-Kommentars und jedes offenen Threads.
  - **Umsetzung (entschieden), Mergen durch Claude (2026-11-20):** Claude kann PRs der eigenen Sitzung über das App-Tool `merge_pull_request` mergen (Repository, PR-Nummer, optional Methode `rebase`, `squash` oder `merge`; ohne Angabe wie Automerge: Rebase, sonst Squash, ein Merge-Commit nur, wenn beides nicht geht); das Backend merged mit einem Installation-Token (`pull_requests: write`, `contents: write`) nur für dieses Repository genau den Head-Commit, PRs, die nicht zur Sitzung gehören, lehnt es ab. Claude merged nur, wenn der Nutzer es angewiesen hat oder Automerge für den PR an ist. Es fragt, wie der Berechtigungsmodus sagt (der Dialog zeigt PR und Methode); bei Automerge ohne Rückfrage, wenn der PR bereit ist (siehe Automerge). `gh` bleibt nur lesend.
  - **Umsetzung (entschieden), PR-Automatik durch Claude schalten (2026-11-20):** Claude kann Autofix, Automerge und Autoclose der offenen PRs der eigenen Sitzung über das App-Tool `set_pr_automation` schalten (Repository, PR-Nummer, je Schalter an/aus; nicht genannte bleiben), mit denselben Regeln wie die Schalter der Oberfläche (Automerge schaltet Autofix mit ein, Autofix aus schaltet Automerge mit aus). Einschalten nur, wenn der Nutzer es angewiesen hat. Es fragt, wie der Berechtigungsmodus sagt (der Dialog zeigt PR und jeden Schalter). Schalter, die schon so stehen, bleiben unberührt; jede Änderung steht im Verlauf der Sitzung. Während eines Autofix-Laufs (von seiner Nachricht bis zum Ende des Turns, den sie startet, auch nach einem Neustart des Prozesses) kann es Schalter nur ausschalten: Der Lauf arbeitet mit nicht vertrauenswürdigem Inhalt von GitHub, der kein Fixen oder Mergen einschalten darf. Wartet Automerge auf die Entscheidung des Nutzers (`request_owner_decision`), kann Claude es nicht einschalten; Ausschalten beendet das Warten nicht, nur die nächste Nachricht des Nutzers. Geschützt ist so nur der Autofix-Turn selbst: Text von GitHub bleibt im Gespräch, in späteren Turns (und bei dem, was Claude mit `gh` liest) schützt wie bei `merge_pull_request` nur der Berechtigungsmodus.
  - **Umsetzung (entschieden), mehrere PRs pro Sitzung (2026-11-20):** Eine Sitzung kann mehrere PRs eines Repositories gleichzeitig bearbeiten, jeden in einem eigenen Klon mit eigenem Branch. (1) Den weiteren Branch legt Claude selbst aus dem Gespräch heraus an, mit dem App-Tool `add_branch` (Repository, optional Basis-Branch, sonst der des ersten Klons; kurzer Grund), ohne Button in der Oberfläche und ohne Freigabe: Es klont nur ein Repository, das die Sitzung schon hat; Pushes und PRs fragen wie bisher. Auch der nächste PR nach einem Merge entsteht so, statt den Sitzungs-Branch umzuschreiben. Lokale Projekte ohne Remote werden abgelehnt. (2) Die Branches sind durchnummeriert, `claude/<slug>-2`, `-3`, … (keine Inhalte in Branch-Namen; die kleinste Nummer, die kein Klon der Sitzung hat oder hatte; ein Klon, der nicht angelegt werden konnte, wird sofort vergessen und gibt seine Nummer frei), der Klon liegt neben dem ersten (`<owner>/<name>-2`). (3) Wird der PR eines Klons gemerged oder geschlossen, kommt kein anderer offener PR aus ihm und hat die Sitzung noch ein anderes Verzeichnis, in dem Claude arbeitet (das letzte bleibt immer; seit dem Wechsel des Arbeitsverzeichnisses gilt das auch für den ersten Klon), entfernt die App den Klon, sobald der Turn der Sitzung vorbei ist (wie bei Autoclose), aber nur, wenn nichts davon auf GitHub fehlt (dieselbe Prüfung wie bei Autoclose); sonst bleibt er, mit Hinweis im Verlauf. Die Sitzung läuft in ihren anderen Verzeichnissen weiter; Claude erfährt es mit der nächsten Nachricht. Wo ein Klon über das Repository gesucht wird, entscheidet der Branch (beim PR sein Head-Branch); die Routen pro Klon nehmen `?branch=`, das bei mehreren Klonen eines Repositories nötig ist.
  - **Umsetzung (entschieden), Arbeitsverzeichnis wechseln (2026-11-20):** Die Klone einer Sitzung sind gleichberechtigt; einer ist gerade das Arbeitsverzeichnis von Claude Code (dessen `CLAUDE.md`, Settings, Hooks, Skills und Memory gelten), die anderen sind zusätzliche Verzeichnisse. Claude wechselt es selbst aus dem Gespräch heraus mit dem App-Tool `switch_directory` (Repository, bei mehreren Klonen der Branch), ohne Button und ohne Freigabe: Es startet Claude Code nur in einem Verzeichnis der Sitzung neu. Gespeichert wird die Wahl sofort (auch über Neustarts der App), wirksam, sobald der Prozess neu starten kann: Er wird beendet, sobald kein Turn läuft und nichts ihn hält (Hintergrund-Tasks, Claudes eigenes Warten mit `work`, Previews seiner Dev-Server endeten mit ihm), also am Ende des Turns, sofort im Leerlauf oder nach der Hintergrundarbeit; die nächste Nachricht startet Claude Code im neuen Verzeichnis und setzt dieselbe Unterhaltung per `resume` fort. Getestet am 2026-11-20 mit Claude Code 2.1.322 (auch dem Binary des Agent SDK), mit Haiku in einer Minimalumgebung: Claude Code findet das Transkript über die Session-ID aus jedem Verzeichnis, schreibt im ursprünglichen Projektordner weiter und vermerkt das aktuelle Arbeitsverzeichnis je Eintrag; hin und zurück blieb die Unterhaltung erhalten. Es wird also nichts kopiert; die App liest das Transkript aus dem Projektordner des ersten Verzeichnisses, sonst aus jedem. Soll der Klon des Arbeitsverzeichnisses nach seinem PR entfernt werden, wechselt die App vorher in einen anderen Klon (einen weiteren desselben Repositories, sonst das erste verbliebene Verzeichnis) und sagt es Claude. Kosten: der erste Turn nach einem Wechsel läuft ohne Prompt-Cache. Settings, Hooks und Skills des neuen Arbeitsverzeichnisses gelten ohne eigene Freigabe: Wählbar sind nur die eigenen Klone und Verzeichnisse der Sitzung, und Claude könnte dieselben Dateien auch ins aktuelle Arbeitsverzeichnis schreiben (gleiche Angriffsfläche). Entfernt die App den Klon des Arbeitsverzeichnisses, wartet sie damit, solange der Prozess für Hintergrundarbeit oder Previews bleiben muss; scheitert das Entfernen, bleibt das Arbeitsverzeichnis, wo es war, und Claude erfährt nichts.
  - **Umsetzung (entschieden, 2026-11-20), welche Klone nach dem PR gehen:** Die App entfernt nach dem Merge oder Schließen seines PRs jeden Klon, nicht nur weitere aus `add_branch`, also auch den einzigen Klon eines Repositories (den ersten der Sitzung oder einen mit `add_repository` hinzugefügten), solange ein anderes Verzeichnis bleibt, in dem Claude arbeitet; für einen weiteren PR dieses Repositories legt Claude mit `add_branch` wieder einen Klon an. Schließungen, die frühere Versionen nicht vermerkt hatten, gelten als erledigt (außer solchen, die Autoclose noch abarbeiten muss), damit das erste Abfragen nach dem Update keine Klone älterer Sitzungen entfernt.

**Claude-Anmeldung:** Claude Code meldet sich über das Claude-Konto (Abo) an, nicht per API-Key. Auf der Devbox ist es der Login des Benutzers in `~/.claude`, im Container liegen die Anmeldedaten im Volume des Claude-Verzeichnisses und überstehen so Neustarts.

## Globale CLAUDE.md im Container

Eine globale CLAUDE.md im Image (bzw. im Claude-Verzeichnis; auf dem NixOS-Dienst als Anhang an den System-Prompt) gibt allen Sitzungen gemeinsame Regeln vor. Erste Punkte, noch zu ergänzen:

- **Werkzeuge:** Fehlende Tools über Nix holen; Repos mit `flake.nix` immer in deren Dev-Shell bauen und testen.
- **Sitzungsklone:** Nur in den Klonen der eigenen Sitzung arbeiten, nie im lokalen Spiegel eines Repos.
- **Mehrere Repos:** Zusätzliche Repositories liegen als eigene Sitzungsklone vor; Änderungen dort ebenfalls nur auf dem Sitzungs-Branch.
- **Verzeichnisse:** Feste Struktur für Spiegel, Sitzungsklone und Scratch-Verzeichnisse.
- **Git:** Claude darf selbst committen und den Sitzungs-Branch mit den Zugangsdaten des Benutzers pushen (gefragt wird je nach Berechtigungsmodus); andere Branches, Force-Push und das Umschreiben veröffentlichter Historie nur auf ausdrücklichen Wunsch.

## GitHub-Anbindung

Die Anbindung läuft über eine eigene GitHub App.

- Die App wird im Nutzer-Account und in den gewünschten Organisationen installiert; dort wird festgelegt, auf welche Repositories sie zugreift.
- Das Backend erzeugt daraus kurzlebige Installation-Tokens für Repo-Liste, Klonen, Pushen per Knopf, PRs und die PR-Automatik. Sitzungen bekommen keine.
- Private Key und App-ID liegen als Secrets im Container, nicht im Image.

**Pushen und Pull Requests:** Beides geht auf zwei Wegen.

- **Per Knopf:** Die Oberfläche bietet pro Repository der Sitzung „Push“ und „PR erstellen“ an; das Backend führt es mit einem Installation-Token aus.
- **Durch Claude:** Claude kann den Sitzungs-Branch selbst pushen (`git push` mit den Zugangsdaten des Benutzers: Git-Konfiguration, `gh`-Credential-Helper, SSH, wie im Terminal) und über ein eigenes Tool `create_pull_request` (Repository, Titel, Beschreibung, Basis-Branch) einen PR anlegen, den die Sitzung dann anzeigt und die PR-Automatik verfolgt. Ob dafür gefragt wird, entscheidet der Berechtigungsmodus der Sitzung wie bei jedem Tool. Auf Review-Threads dieser PRs antwortet Claude mit dem Tool `reply_to_review_thread` und löst sie damit auf (siehe GitHub-Tokens).
  - **Umsetzung (entschieden):** Der frühere Credential-Helper der App, der GitHub-App-Tokens nur nach einer Freigabe herausgab, entfällt samt Endpunkt und Sitzungs-Tokens. `origin` eines GitHub-Klons ist die HTTPS-URL, sodass der Credential-Helper des Nutzers für `https://github.com` greift (oder eine `insteadOf`-Umschreibung auf SSH in seiner Konfiguration). Der Freigabe-Dialog zeigt weiter, was ein `git push` aktualisieren würde, mit Warnungen für alles außer dem Sitzungs-Branch.
- **Entwürfe:** **Umsetzung (entschieden):** Ein offener Entwurfs-PR erscheint überall, wo die App den Stand eines PRs zeigt, grau als „Draft“ wie auf GitHub, nicht grün als „Open“.
- **CI-Checks am PR:** Jeder offene PR der Sitzung zeigt den Stand der Checks seines Head-Commits, wie die Claude-Code-Oberfläche.
  - **Umsetzung (entschieden):** Eine Zeile mit dem Gesamtstand (rot: einer schlug fehl, gelb: welche laufen, grün: alle durch) und den Zahlen („Checks: 1 failed, 2 running, 5 passed“); Antippen klappt die Liste der einzelnen Checks auf (Zustand, Name, Link zu den Details), fehlgeschlagene zuerst, dann laufende. Für alle offenen PRs, auch ohne PR-Automatik. Gelesen beim Anlegen des PRs und bei jedem neuen Head-Commit, bei Webhooks zu Checks und Statuses, mit den Lesungen der PR-Automatik, und solange jemand die Sitzung ansieht alle 30 Sekunden, während Checks laufen (höchstens eine Stunde lang, ein Commit ohne Checks 5 Minuten lang; sonst alle 5 Minuten). Der Stand wird gespeichert; Änderungen an Checks und ein Abgleich ohne Änderung (gleicher Titel, Zustand, Entwurf und Head-Commit) schieben die Sitzung in der Liste nicht nach oben.

## Spätere Ausbaustufen

Nicht Teil der ersten Version, aber in der Architektur mitzudenken:

- **Dateibrowser:** Verzeichnisbaum der Klone einer Sitzung, Dateien mit Syntax-Highlighting ansehen, geänderte Dateien markiert, Dateien per Klick als Referenz in den Prompt übernehmen. **Umsetzung (entschieden):** Eigene Seite „Files“ der Sitzung mit einem Baum pro Verzeichnis (die Dateien wie für `@`: von git verfolgte und unverfolgte, ohne ignorierte), Filter über alle Pfade, von der Sitzung geänderte Dateien (wie auf der Changes-Seite) markiert, Ordner mit Änderungen darunter mit Punkt; Dateien öffnen im vorhandenen Dateiviewer (Highlighting, Markdown, Bilder, PDF, HTML in Sandbox); „Reference in message“ führt zurück in die Sitzung mit `@pfad` im Eingabefeld. Gelesen wird nur innerhalb des Verzeichnisses (auch über Symlinks nicht hinaus).

* **MCP-Server, Slash-Commands und Skills:** Kommen bereits wie im Terminal aus dem `~/.claude` des Benutzers und den Repos. **Umsetzung (entschieden):** Autovervollständigung im Eingabefeld der Sitzung, wenn die Nachricht mit `/` beginnt: die Befehle und Skills, die Claude Code der Sitzung meldet (vor dem ersten Prozess die des Benutzers und die eigenen von Claude Code), ohne die an ein Terminal gebundenen; die Nachricht geht unverändert an Claude Code, das den Befehl ausführt.

* **Antwortvorschläge:** Wie im Terminal und in der Desktop-App schlägt Claude Code nach einem Turn die nächste Nachricht des Nutzers vor, die er übernehmen kann. **Umsetzung (entschieden):** Wie in Terminal und Desktop-App als Platzhaltertext des leeren Eingabefelds, solange kein Turn läuft und noch keine Nachricht gesendet wurde. Senden bei leerem Feld schickt den Vorschlag unverändert ab (nur wenn er ganz sichtbar ist, höchstens 8 Zeilen); Tab oder ein Bearbeiten-Knopf neben Senden (für Touch-Geräte) übernimmt ihn ins Eingabefeld zum Ändern. Er bleibt nach einem Neuladen erhalten. Ausschalten über die Claude-Code-Einstellung `promptSuggestionEnabled: false`.

* **Verstellbare Spalten:** Auf breiten Bildschirmen lassen sich die Sitzungsliste links und die Sitzungsdetails rechts neben einer offenen Sitzung in der Breite ändern. **Umsetzung (entschieden):** Ein Griff am Rand der Spalte (Ziehen, oder fokussieren und Pfeiltasten; Doppelklick oder Enter stellt die Standardbreite wieder her). Die Breiten gelten pro Browser (`localStorage`), nicht pro Sitzung; Grenzen: Liste 240–560 px und höchstens 30 % des Fensters, Details 280–640 px und höchstens 34 %, damit das Gespräch Platz behält.
